# Live SWOT (Scadable) - Team 10 (Niche)


## 1. What Needed to Improve

After D2, the biggest area we needed to improve was the reliability and consistency of Live SWOT’s competitor research workflow. Users could add a competitor, run research, and view SWOT findings, but the results were not always consistent. Some competitors received feature scores while others didn’t, citations were sometimes missing or pointed to the wrong source, and the overall SWOT didn’t always reflect SCADABLE’s perspective. There were also problems behind the scenes. When the scraper or LLM failed, the system could quietly fall back to mock data, making it difficult to tell whether results came from real research. Another area that needed improvement was API cost tracking. We had limited visibility into the costs of individual AI calls and entire research runs, which made it harder to monitor spending. Research also depended mostly on users manually starting new runs, meaning existing information could become outdated. Since Live SWOT’s main purpose is to provide SCADABLE with trustworthy and up-to-date competitive intelligence, improving these areas became our priority for D3.

We identified these areas for improvement through our D2 demonstrations, testing, partner meetings, and team retrospective. One clear example was the difference in results between competitors. Vanta returned 11 extracted features, 11 feature scores, and 7 SWOT findings, while Foresite returned 13 features with no scores, and Drata returned only 2 features with no scores. Our partner also suggested improvements to citation accuracy, the SWOT layout, and the amount of information displayed for each research run. We also recognized the need for better API cost tracking so we could understand where our spending was coming from. During our retrospective, we identified late integration between the frontend, backend, scraper, and LLM components, along with insufficient end-to-end testing, as reasons some of these issues went unnoticed until close to the deadline. Based on these findings, we decided to focus D3 on improving research reliability, consistency, cost visibility, and the overall user experience rather than simply adding more features.

## 2. What You Did

We reorganized research into two LLM stages: source-cited fact extraction followed by a comparison that generates SCADABLE-relative SWOT findings, competitor findings, and feature scores. This removed the intermediate company-analysis step and preserved complete extractions for later comparisons. Citation and feature-pair validation keep findings tied to the correct companies and comparable capabilities. Revision guards prevent older comparisons from overwriting newer results, while valid previous scores remain available when comparisons fail. Scraping now uses analysis-aligned objectives, conservative consent/carousel cleanup, exact duplicate detection, and approximate topic-coverage hints. Duplicate pages retain their source files but avoid repeated assessments and analysis inputs. At each scoring checkpoint, we update Decisions with topic hints from useful, unique pages so similarly relevant candidates can address research gaps. We also skip known redirect duplicates and use exact Markdown fingerprints to reuse assessments, reducing repeated API work while preserving source files and links. Production crawl and LLM failures surface as failed runs instead of silently returning mock findings. These changes required coordinating scraper exports, extraction schemas, citation indexes, and backend persistence without losing source evidence.

We also connected scraper Decisions and LLM usage to Langfuse and backend research-run IDs, added cost retrieval with incomplete-data handling, and displayed available costs on Agent Runs. Analysis-policy versioning prevents unchanged-content reuse from bypassing updated processing rules. An opt-in scheduler queues refreshes from persisted run history, prevents overlapping research, and recovers abandoned jobs. Competitor profiles now use backend feature scores, job-posting counts, activity, and refresh information, with improved chart behavior and polling. Source-cited conflict extraction and an optional conflicting-data table were added, although mapping stored conflicts into the profile API remains incomplete. Accessibility work added keyboard navigation, focus management, and clearer form validation; sanitized errors avoid exposing internal details. GitHub Actions now runs backend and scraper tests, scraper lint/format checks, and frontend lint. Integration work included adapting mocks and package installation, combining tracking with coverage-aware selection, and testing failure, reuse, citation, cost, and freshness behavior across layers.

## 3. Before vs. After

| Area | Before (D2) | After (D3) |
|---|---|---|
| **AI research pipeline** | Research used several LLM steps, including a separate company analysis step. Findings could cite the wrong company or switch whose point of view the SWOT was written from. | We have to two stages now. Fact extraction with citations, then a comparison that writes the SWOT from SCADABLE's point of view and scores features. Citations and feature pairs are checked so each finding belongs to the right company. |
| **Feature scores** | Scoring was inconsistent. Foresite had 13 features and no scores, and Drata had 2 features and no scores. A failed comparison could wipe out existing scores. | Any competitor with features is scored, and the chart shows SCADABLE's score next to the competitor's. Previous scores are kept if a comparison fails, and a longer comparison timeout lets slower comparisons finish. |
| **Scraping quality** | Cookie banners, duplicate pages and redirect aliases were all sent for assessment and analysis, which repeated API work. | Boilerplate cleanup, exact duplicate detection and coverage hints steer the crawl toward missing topics. Duplicates reuse earlier assessments while keeping their source files and links. |
| **Failed research** | When a site blocked the scraper, the backend used sample pages and marked the run successful. Drata's profile was built this way. | A failed crawl or LLM step fails the run with a clear message. Sample data is only used in local development when turned on explicitly. |
| **Cost visibility** | Nobody could see what a run cost so we couldn't reliably keep track. | Each run records its LLM and scraper page selection costs from Langfuse, and the Agent Runs page shows the cost per run and a weekly total. Incomplete costs are never shown as final, and run steps now show what actually happened, including on failed runs. |
| **Freshness** | Research ran only when a user started it. The overall SWOT could show old results after a failed comparison. | A scheduler can refresh competitors from run history, prevent overlapping runs and recover stuck jobs. It is built but turned off for D3. The overall SWOT only shows results that match the latest data, and analysis version checks stop old results from being reused after the analysis rules change. |
| **Competitor profile** | Open roles and next refresh time were not analyzed and displayed. | The profile shows job posting counts, the next refresh time, recent activity and feature scores from the backend, with better polling while scores are being generated. |
| **Conflicting data** | Not supported. | The LLM extracts conflicting claims with sources, and the frontend has an optional table for them. *Partial: stored conflicts are not yet sent to the profile page.* |
| **Accessibility and errors** | Forms had limited validation and focus handling, and raw internal errors could reach users. | Keyboard navigation, focus traps in dialogs, clearer form validation and Lighthouse evidence. Error messages are sanitized in both the API and the UI. |
| **Testing and CI** | No automated checks ran on pull requests. | GitHub Actions runs three checks on every pull request. The scraper check runs lint, formatting and tests. The backend check runs tests against PostgreSQL, including LLM adapter and cost tests that don't spend OpenAI tokens. The frontend check runs lint. |

## 4. Reflection

What worked well was treating reliability as a cross-layer problem instead of a list of isolated bugs. Making failures visible had the largest impact on trust: once failed crawls stopped returning mock pages and stale overall SWOTs were flagged instead of silently replaced, test runs exposed real problems, such as sites that block crawlers, that fallback data had previously hidden. Guarding stored results also paid off. Revision checks and score preservation meant a slow or failed LLM comparison could no longer erase or overwrite newer findings. Process changes supported this work: GitHub Actions ran backend, scraper, and frontend checks on every pull request, and running the backend suite against PostgreSQL caught integration issues that in-memory tests missed. Langfuse cost tracking gave us measurable evidence of where the pipeline spends money, rather than estimates.

Integration was harder than expected. Most D3 improvements touched several layers at once; for example, keeping feature scores trustworthy required coordinated changes to the LLM output, orchestrator persistence, the profile API, and chart behaviour, so small schema changes caused follow-up fixes elsewhere. Asynchronous behaviour was the hardest to reason about: background comparisons, delayed Langfuse cost ingestion, and concurrent refreshes produced race conditions and one order-dependent test that only appeared with a real database. We also learned that merging directly to `main` bypassed review and CI, so we moved to pull requests for every change. Finally, the deployed Railway backend sometimes lagged behind `main`, meaning a feature could pass every test and still not be visible to the partner.

For D4, we will finish features that D3 left partially connected rather than start new ones: mapping stored conflicts into the profile API so the conflicting-data table shows real data, enabling scheduled refreshes, and resolving known edge cases such as competitors that share a name. We also plan to redeploy and verify every merged change on the live application before demos, and to integrate the frontend, backend, scraper, and LLM layers earlier so that cross-layer problems surface during development instead of at the deadline.
